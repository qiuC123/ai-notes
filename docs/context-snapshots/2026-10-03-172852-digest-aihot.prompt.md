## 我的目标和不能随意改变的规则

我需要的是值得用、值得学、值得尝试的项目精选，以实用开源项目为主，也兼顾有趣的项目和少量开发机会。热度只是发现线索，不是最终目标。不要把项目变成 AI 新闻转载站，也不要只推荐我个人已经在用的工具。

1. 八个主栏目保持为：开源项目、Skills、AI 应用、Agent 框架与编排、MCP 服务与连接器、模型与运行工具、游戏、博客/帖子/访谈。一项一个主栏目，空栏目省略；CLI、自托管、平台等做标签，不按语言分类。
2. 日榜 5–8 条，周榜 20–25 条并通常有 3 个非阅读重点（非阅读内容不足时取实际数），月榜至少 20 条。共享候选库，各期独立筛选；跨级可重复但要补充阅读价值。同级默认不重推，只有真实且尚未报道的重要更新才可再次入选。
3. 北京时间自然周期：每天 19:00 积累候选，次日 09:00 做前一天日榜，周一 10:00 做上个完整自然周，月初 11:00 做上个自然月。数量不足按已有规则交付或留稿，不编造内容、不倒填不属于原月的项目。
4. Show HN、搜索、榜单和 AIHOT 等聚合平台用来发现，关键事实回到仓库、官网或作者原文核验。Hugging Face 作为直接来源；HelloGitHub 不再作为候选来源，只参考选题和编辑方法，不能采月刊补数。
5. 首次发现、发布日期/更新事件、抓取和核验时间分开。未知保持未知；文档、演示与实测不得混淆。开发机会最多 2 条且不计入精选数量。
6. 保留批次幂等、原始来源、全部同级归档去重、不可覆写归档、草稿重试边界和通知去重。首次归档要求准备与逐项核验均在真实执行前 24 小时内，不能靠改时间戳延长有效期。保留飞书、Pi、项目共学及旧 Release 管道的独立边界。

快照时间是 2026-10-03 17:29 北京时间，当时有 103 个候选身份、287 条观察、47 个批次、22 期归档和 3 份日榜草稿。169 条入选记录不等于 169 个不同项目。这些是历史观测，不要当作讨论时的实时状态，也不要把有批次日期等同于全天候完整采集。

当前三榜 CLI 负责保存、校验、去重和归档，检索、原文核验、筛选和写作仍由 Codex 会话执行；`dispatch` 只返回动作。上传 GitHub 与让程序在云端独立持续运行是不同阶段。

## 请输出一份可以交给 Codex 实施的计划

先用通俗中文给出推荐路线及理由，然后按以下顺序展开：

1. **现状与问题。** 哪些已有能力应保留？哪些能力尚依赖 Codex？针对我觉得入选规则有问题，区分来源覆盖、候选召回、过滤、评分、原文核验和文章表达的问题；不要把“多接信息源”当成万能解法。特别评估候选按 URL 排序后截断的影响，并说明还需要什么数据才能确认。
2. **AIHOT 借鉴对照表。** 列出采集适配器、队列、分阶段筛选、重复评分、标注评测、事件归并、请求复用、成本预算、后台编辑与多端输出；每项标为保留现有 / 借鉴机制 / 直接复用 / 暂不采用，并写出代码依据和本项目需要改什么。区分已实现事实与建议；AIHOT 示例来源不等于完整生产来源。
3. **筛选质量方案。** 围绕实用价值、适用读者、上手成本、证据、差异化和可学习性提出可解释方案；热度只辅助。设计可保存的入选/淘汰理由、少量代表性人工标注、开发集与留出集、漏选/误选分析及验收办法。不要一开始堆复杂评分维度；不要凭空承诺质量提升百分比。解释是否值得沿用上游两次模型评分及其成本。
4. **架构路线比较。** 比较继续扩展现有 Python、抽取 AIHOT 机制/组件、直接 fork AIHOT 三条路径，从迁移风险、现有规则兼容、维护量和长期成本作选择。给出简明数据流和模块职责，说明每一步由代码、模型还是人负责。没有实际需要就不引入 PostgreSQL、向量数据库、微服务或全量 TypeScript 重写。
5. **分阶段实施清单。** 先本地改进与质量基线，再独立后台执行，最后云部署。每阶段列出改动模块、输入输出、验收标准、与改动相称的测试、失败恢复和回退方式。明确第一阶段最小交付，区分必须做、后续做和本轮不做；保留已有数据及文章。
6. **上云条件与成本。** 明确服务器/托管、模型 API、数据库、来源服务、备份和日志的需要；给调用量/频率驱动的预算计算方法，未查到当前价格就保留未知。说明真实运行数据如何私下迁移、如何校验归档与观察、如何避免本地云端双重调度、如何停用旧执行器和回退。先完成可审查方案，不直接购买、部署或发布。
7. **Dot 的位置。** 如果引入 OpenAI Dot，先核对官方当前能力和额度政策，再说明适合做协调、查看、提醒还是执行。不要假定“24 小时可用”等于能托管任意常驻服务，也不要假定所有任务和模型调用免费。核心持久化与调度必须有明确归属，不依赖聊天上下文充当数据库。

请清楚区分“代码/数据已经证明”“根据证据推断”“建议新增”“仍待确认”。本轮只规划，不写代码、不修改自动化、不部署、不发布。优先给出可讨论的完整初稿，对未知条件使用标明的合理假设；最后最多问 3 个真正影响路线的关键问题，不要用长问卷代替方案。
