## 独立执行的实际边界

`digest_runtime schedule` 在入口只计算一次真实时间 dispatch。`work` 每次处理一条已入队任务，后台宿主可以重复调用直到 idle；租约及业务键防止同一条任务重复认领。仅单台主机、单工作进程作为部署目标，SQLite 不是跨主机任务队列。

生成阶段依次执行：冻结初筛集合和全部初筛理由 → 读取原文 → 抽取带段落绑定的用途、条件、分类与许可 → verified 观察入库 → 形成不可变评分准备包 → 模型分项判断 → 一次有界内容复核 → Python 计算结果 → 草稿/归档。原文提取同时准备短介绍与周/月价值说明，最终只使用入选条目。内容复核使用本次读取的全部来源片段，不能只看评分引用到的网页；暂缓会保留原分数、复核回执和原因，不自动重写或重抽。旧冻结任务按原合同恢复。源码/文档内容不作为模型指令。引用绑定只证明片段存在，模型复核也可能漏报，不能称为实测或自动事实证明。

日/周/月最多初筛 30/80/150、深入核验 12/35/60；不足基本候选数量时最多补采一批 20 条，仍共用初筛/深核预算，时间归属继续由候选查询决定。API 每任务上限 `1 + 3 * 深核上限`，每请求输入不超过 60,000 字符、输出最多 16,384 tokens；失败和结果不确定请求计入预算。预算耗尽记录失败，不扩大执行。月榜不足 20 条保留原月草稿。

`DIGEST_MODEL_BASE_URL`、`DIGEST_MODEL_NAME`、`DIGEST_MODEL_API_KEY` 必须显式配置。使用量保存 provider 返回的 token 数；没有价格配置时费用为 unknown，不推断免费、免 Codex 额度或全天无成本。

请求超时后结果可能已在服务端生成，`retry` 不会重新付款重发同指纹。若服务商能查到原响应，保存含 `provider_receipt`、真实 `completed_at`、`output`、`usage` 的 JSON，执行 `digest_runtime resolve-request --id <request-id> --input <receipt.json>` 后再重试 job。查不到响应时保持失败供处理；没有自动猜测“服务端未执行”的功能。

已明确返回的 429/500/502/503/504 响应可以在核对后显式 `retry-request --id <request-id> --reason <原因>`，再 `retry --id <job-id>`。旧失败回执被完整保留并继续计入请求预算，不自动重发；JSON/契约错误需要修改具体输入或提示词，不当作临时网络失败循环重试。初筛卡片长文本会按字符预算缩短，保留全部审阅 ID；深核仍读原文，不用初筛摘要冒充全文。

通知只保存 outbox：`notices` 查看待交付内容，外部适配器实际交付后才用 `ack --id ... --receipt ...` 确认。当前没有新写飞书/邮件/公众号发送器。原 heartbeat 仍在原 Codex 任务交付；不同时启用独立生产 worker。

## 真实质量验证与未完成项

- 真实候选试评保存到本地 `outputs/digest/selection-trial-2026-10-03.md`；它是模型评审样例，不是新的正式榜单或人工正确答案。
- 需要用户对一组样例进行真实人工选择，才能测量命中率、漏选及调权重。先用 dev 校准，再用独立 holdout 检查，不根据 holdout 反复调门槛。
- 模型服务已指定为智谱官方普通 API，`glm-5.3-flash` / `low`；配置在仓库外，实际用量记录于独立请求账本，账单金额未知。云端执行目标尚待确认；筛选质量、无人值守长期运行、云端部署及通知送达仍需独立验收，不能由样例代码或单次请求代替。
- 当前代码没有自动判定已知仓库的每次发布都是“重大更新”；新事件仍要独立原文证明，不把普通版本补丁算作新增精选。
