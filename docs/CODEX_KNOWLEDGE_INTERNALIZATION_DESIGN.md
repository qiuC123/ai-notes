# Ai Notes — GitHub 项目共学与连接发现设计

Status: Manual vertical slice implemented; complete live acceptance and ten-run validation pending
Date: 2026-09-02
Decisions: [`ADR 0002`](adr/0002-codex-knowledge-internalization-boundary.md), [`ADR 0003`](adr/0003-github-project-learning-and-connection.md), [`ADR 0004`](adr/0004-bounded-dual-entry-discovery.md), [`ADR 0005`](adr/0005-evidence-gated-connection-brief.md), [`ADR 0006`](adr/0006-user-controlled-skill-and-runtime-boundary.md), [`ADR 0007`](adr/0007-replace-hermes-runtime-with-codex-review.md), [`ADR 0008`](adr/0008-manual-learning-card-vertical-slice.md), [`ADR 0009`](adr/0009-separate-co-learning-core-from-legacy-pipeline.md)

## 1. 目标

Ai Notes 帮助用户与 Codex 持续学习值得关注的 GitHub 项目，理解它们的目标、架构、能力和取舍，再与用户正在开发的项目进行对照，发现可复用、迁移、集成或启发新设计的关联机会。

成功不以“每天收集多少条”衡量，而以三个结果衡量：

1. 是否对外部项目形成了超越 Release 摘要的可靠理解；
2. 是否发现了与自有项目具体问题相关的关联机会；
3. 是否通过小实验验证或否定了这些机会。

## 2. 非目标

- 不做全量 AI 新闻聚合；
- 不为了日更或 Top N 强行保留条目；
- 不把社区转述或模型判断当作最终事实；
- 不因为技术栈相同或项目热门就强行建立关联；
- 不未经实验就把外部项目代码或架构搬进自有项目；
- 不读取、写入、检查、触发或优化 Codex 本地记忆；
- 不把所有知识塞进 `AGENTS.md` 或单个超大 Skill；
- 不负责自媒体选题、写作和自动发布。

## 3. 项目共学闭环

```text
Discover → Select → Understand → Track → Connect → Experiment → Converse → Feedback
```

### Discover and Select — 发现与选择

从官方仓库、技术作者和高质量发现渠道中寻找外部学习项目。选择标准不是热度，而是项目是否有清楚的问题边界、可核验资料，以及与自有项目发生关联的可能性。

### Understand — 理解项目

围绕一个外部项目形成项目理解：它解决什么问题、服务什么场景、核心抽象是什么、架构边界在哪里、公开接口有哪些、做了哪些关键取舍、什么情况下不适合使用。结论必须能回到官方文档、代码或可复现实验核验。

### Track — 跟踪演进

Release、Changelog 和重大 PR 用于跟踪项目演进，但它们只是触发重新学习的信号，不是完整知识。

### Connect — 连接自有项目

把外部项目中的可迁移能力与自有项目中的具体问题或目标对照，形成“项目关联机会”。每个机会至少回答：

- 自有项目当前遇到什么具体问题？
- 外部项目的哪个能力或设计可能有帮助？
- 两者的集成边界在哪里？
- 预期收益、成本和风险是什么？
- 用什么最小实验可以证伪？

相似技术栈、相似关键词或项目热度不能单独构成关联机会。

### Experiment — 验证实验

先做低成本、可回滚的小实验，例如接口原型、局部替换、性能基准或工作流演练。实验成功才提出正式采用建议；实验失败也要保留原因，避免重复踩坑。

### Converse — 进入对话

项目理解、关联机会和实验结果进入用户与 Codex 的正常讨论或真实开发任务。项目不创建专门的记忆写入流程，也不把“是否形成记忆”作为成功条件。

Codex 是否从对话中自动提取记忆、何时提取、如何合并和召回，全部由 Codex 自身决定。Ai Notes 不读取、写入或检查 `~/.codex/memories/`，也不调整记忆配置来影响结果。必须长期可用的内容保留在知识文档、Skill 或 `AGENTS.md` 中，不能只依赖记忆召回。

### Feedback — 反馈

记录关联机会是否成立、实验是否改善了自有项目、哪些判断需要修正。反馈同时更新外部项目理解、自有项目需求和项目优先级。

## 4. 三个最小对象

### 外部项目档案

- 仓库和核验版本；
- 解决的问题、适用场景和不适用场景；
- 核心能力、架构边界和公开接口；
- 关键设计取舍及证据；
- 最近值得重新学习的实质变化。

### 自有项目画像

- 项目目标和当前阶段；
- 关键架构与约束；
- 当前问题、技术债和计划；
- 允许实验的边界。

### 项目关联机会

- 外部项目中的可迁移能力；
- 对应的自有项目问题；
- 连接方式和预期收益；
- 成本、风险和不适用条件；
- 最小验证实验及结果。

### 第一版数据契约

第一条垂直闭环只建立三个版本化 Schema：

- `learning-queue.v1`：核验版本、外部证据入口和自有项目引用；
- `learning-decisions.v1`：项目理解、关联假设、双侧证据、风险和下一步；
- `learning-run-manifest.v1`：运行状态、缺失范围、输入输出指纹和规则版本。

第一版不建立完整项目档案数据库。共学卡片在主对话中展示；本地仅保留三十天的机器可读 JSON、运行清单和必要外部证据快照，不默认生成 Markdown 学习报告。长期账本中的自有项目证据只保存相对路径、symbol 或紧凑行号、commit/工作区指纹和不含源码的说明。

## 5. 双入口发现与每日预算

项目候选有两个入口，并进入同一套核验、理解和关联流程：

1. **主动发现候选**：Codex 每日从 GitHub 主动搜索；
2. **人工提名候选**：用户在正常对话中提交 GitHub 地址，立即获得更高处理优先级。

人工提名默认只分析一次。只有用户明确说“持续关注”时，项目才进入长期监控，避免把每个有趣链接都变成永久订阅。

关联分析只读取当前工作区或用户明确登记的自有项目，不自动扫描其他开发目录。MVP 只使用当前工作区，后续才增加授权自有项目清单。

每日发现预算采用：

- 80% 面向自有项目的明确问题、依赖和相邻生态；
- 20% 用于问题结构或设计方法可能迁移的相邻探索；
- 每日关联简报最多输出三个关联机会；
- 没有合格关联时输出健康空结果，不为日更降低门槛。

每次手动触发主动发现时，元数据初筛最多二十个候选，深读最多五个，最终仍最多输出三个关联机会。达到匿名 GitHub 限额或必要来源不完整时返回 `partial`，不能用扩大搜索或降低证据门槛补足数量。

无人值守的每日任务只允许搜索、读取、核验、分析和报告。确需读取完整代码时可以使用隔离的只读缓存，但不得运行陌生代码、安装依赖、修改自有项目或执行实验；这些动作必须回到正常对话并获得用户明确授权。

## 6. 分析、交付与状态边界

每日关联简报固定返回一个长期存在的“共学主对话”，不为每天创建新任务，也不生成需要用户维护的日报文档。

每次运行自动从当前项目的 README、CONTEXT、ADR、依赖、TODO 和近期改动提取搜索方向；用户可以在对话中临时指定关注主题，但不需要维护关键词表，也不能只依赖 Codex 记忆决定搜索范围。

从代码、TODO 或近期改动推断的问题必须标记为“推断项目问题”。它可以参与关联排序，但在创建实验任务前必须由用户确认，不能包装成已确认需求。

候选采用两阶段分析：

1. 使用仓库元数据、README 和 Release 进行低成本初筛；
2. 只对少量高分候选读取官方文档、核心代码和关键 Issue/PR。

一个结果只有同时具备以下双侧证据时，才能成为项目关联机会：

- 外部项目的具体能力、接口或设计证据；
- 自有项目中的具体问题、目标或代码位置。

缺少任意一侧证据的结果只保留为探索线索，不进入每日最多三个关联机会的简报。

通过证据门槛后不使用复杂百分制。候选按与自有项目的相关性、可行动性、学习价值和新颖性给出可解释优先级。Star、Trending 和模型主观偏好不能代替排序理由。

许可证不兼容、长期无人维护或存在明显安全风险的项目仍可以作为“仅学习项目”报告，但必须阻止复制、集成或实验，直到对应风险被单独解决。

Fork 默认回到上游仓库核验；只有 fork 的独有修改本身是学习对象时才分析 fork。归档、许可证不明或许可证不兼容的项目可以生成标记清楚的共学卡片，但只能作为仅学习项目。明显恶意、冒充官方身份或无法核验来源的候选直接拒绝，不进入深读。

系统只持久化不能安全重新推导的运行状态：关注项目、上次检查位置、证据引用、关联结论、实验结果和用户反馈。项目摘要、AI 问答和 Codex 记忆副本不属于持久化范围。

日常学习结果默认只进入共学主对话，不自动生成知识文档。只有用户明确说“沉淀这个结论”，或一个验证实验已经确认结果，才允许把结论写入对应项目文档或 ADR；创建或更新 Skill 仍遵循单独授权。该规则避免把未经验证的模型分析固化为事实。

单个项目以“共学卡片”交付，固定回答：项目解决的问题、核心抽象、关键架构/接口及官方证据、与目标自有项目的具体关联、不适用条件/许可证/风险，以及下一步反馈。没有双侧证据时必须明确写“暂无可验证关联”，不能为完成模板强行联想。

用户在自然对话中的反馈被归入四类：

- `继续讨论`：继续当前关联，不自动长期关注项目；
- `忽略`：当前关联冷却三十天，不屏蔽整个项目或主题；
- `持续关注`：加入项目监控，只在实质变化或新关联时再次报告；
- `做实验`：移交到独立 Codex 任务，必要时使用独立 worktree，共学主对话不直接修改代码。

只有用户明确表达的反馈才能写入长期账本。Codex 可以提出建议分类或在含义不清时询问，但不能把未回复、跳过或结束对话推断为“忽略”。

同一项目默认进入三十天冷却期；实质 Release、新关联或用户明确持续关注可以提前解除。

MVP 自动发现只覆盖公开 GitHub 仓库；自有项目可以是当前本地私有代码。完成十次手动触发的共学运行，其中至少三次来自用户提交项目、三次来自 Codex 主动发现，并且至少六次获得继续讨论/持续关注/做实验反馈且双侧证据错误不超过一次后，才创建每天 08:30（Asia/Shanghai）的定时任务。

外部原始快照保留三十天；关注状态、证据引用、反馈和实验结果长期保留；系统不复制保存自有项目源代码。

## 7. 交互入口与实现边界

MVP 前十次运行不创建 Skill，由共学主对话读取本设计和项目语境，并调用 Python 程序完成确定性采集、缓存、账本和校验。达到自动化准入门槛后，只有用户明确要求“创建共学 Skill”，才把稳定工作流固化为版本化 Skill；以后每次创建或更新仍需用户授权。定时任务只能调用用户批准的固定版本，不能自行创建、改写或升级 Skill。

人工提名采用最小歧义入口：

- 在共学主对话中，单独发送 GitHub 项目地址即视为一次性人工提名；
- 在其他对话中，只有明确说“学习这个项目”等意图才触发 Ai Notes；
- 裸链接不自动加入持续关注，持续关注仍需明确指令。

普通仓库地址默认核验其默认分支当时的明确 commit，并记录 SHA 和核验日期；Release、PR 或 Issue 地址以指定对象为入口，同时补足所属项目理解；用户给出 tag 或 branch 时严格按指定版本分析。任何输出都不能只引用会漂移的仓库首页来代表核验版本。

自有项目通过“将当前项目加入 Ai Notes”登记。登记项保存规范化本地路径、仓库标识、显示名称和加入原因。MVP 只登记当前项目；后续支持多个授权项目时，每日最多三个关联机会是所有项目共享的全局预算，每条结果必须标注目标自有项目。

自动运行可以写入 Ai Notes 自身批准的 `data/` 和 `outputs/` 运行目录，但对所有自有项目保持只读。它可以读取未提交工作区和 diff 以理解当前问题，但不得复制、持久化或输出完整 diff，也不得修改、暂存或提交这些变更。

持久化格式保持简单：

- YAML 保存人类维护的登记和策略配置；
- JSONL 保存只追加的关注、游标、关联、反馈和实验账本；
- JSON/Markdown 保存可校验的单次运行产物。

上述 Markdown 只用于已有 Release 流水线或用户明确要求的可读导出；新共学卡片默认只在对话中呈现，其运行留存以 JSON 和 manifest 为准。

Schema、策略文档和经批准的 Skill 版本进入 Git；运行账本、缓存、原始快照和生成产物保留在本地，不由无人值守任务自动提交。

MVP 只访问无需凭据的公开 GitHub 信息。遇到匿名 API 限额时把运行标记为 `partial`，不得把不完整结果表述为健康空结果；只有实际限额证明必要且用户另行批准后，才引入专用只读凭据。

深读候选优先使用 GitHub API 和官方网页。只有最终候选在远程证据不足时，才允许把明确 commit 的仓库浅克隆到隔离只读缓存；不得执行 Git hooks、初始化 submodule、安装依赖、构建、测试或运行仓库代码。

Codex 是目标架构中唯一的语义 Agent。它负责理解项目、判断实质变化、建立双侧关联并与用户讨论；Python 负责确定性采集、内容裁剪、状态、Schema 和证据校验。外部 README、Release、Issue、PR 和代码都必须作为不可信数据处理，不能改变任务指令或扩大工具权限。

Codex 任务显式编排三个阶段：先调用 Python Collect 产生有界 `review-queue.json`，再由 Codex 写出符合契约的 `review-decisions.json`，最后调用 Python Finalize。Python 不直接调用 Codex API，不保存模型凭据，也不在后台启动其他 Agent。

目标共学代码进入新的 `ai_notes` 包，避免继续把产品逻辑堆入遗留 `aihot` 包。第一版内部接口为：

```text
python -m ai_notes prepare-learning <github-url> --project .
python -m ai_notes finalize-learning <run-id> --decisions <file>
```

Codex 调用这些内部命令，用户只需要在共学主对话中提交 GitHub 地址。`aihot` 暂时保留当前十二源采集作为候选入口，不先进行全量改名或全面重构；它的语义判断已经改为读取 Codex 决策文件，不再启动其他 Agent。

共学运行固定使用四种状态：`success` 表示全部必要阶段完整，允许“暂无可验证关联”；`partial` 表示版本、官方资料或自有项目证据缺失；`review_failed` 表示 Codex 输出未通过 Schema 或证据校验，可安全重试；`failed` 表示确定性采集、状态或产物写入失败。后三种状态不得伪装成健康空结果。

不引入 Codex 与 Hermes 的多轮讨论。Hermes CLI reviewer 已从运行时代码删除；Release Collect 在没有决策文件时以 `review_failed` 停在队列边界，Codex 生成严格 JSON 后由 Python Finalize 校验。现有 Schema/证据校验、预发布与安全边界、失败重试和历史回测队列继续保留。

## 8. 来源策略变化

现有 12 个 GitHub 仓库应被视为候选“外部学习项目”，而不只是 Release Feed。是否保留同时评估：

- 原始信息是否可信、稳定、可核验；
- 是否能持续产生有实质内容的候选；
- 是否能形成清晰、可核验的项目理解；
- 是否与某个自有项目存在具体关联机会；
- 关联机会是否能通过低成本实验验证；
- 获取、核验和学习成本是否值得。

例如，不计划部署本地模型且自有项目没有本地推理需求时，Ollama、vLLM 和 SGLang 应进入观察名单；只有出现具体项目问题或实验方向时再恢复。项目流行度和 Star 数不能单独决定保留。

旧 12 个来源全部退回候选池，不继承长期关注资格。每日简报中同一 GitHub 组织最多出现一个项目；如果输出三条，至少一条来自不同技术路线。

每个学习项目的证据优先级为：官方代码与文档、Release/Changelog、解释设计取舍的官方 Issue/PR。社区内容只用于发现和提出问题，不能代替项目理解证据。

## 9. 当前实现与缺口

已经实现：

- 12 个官方 Release Atom 采集；
- 正式版硬过滤和缺口补抓；
- Release Codex 决策文件边界和确定性 Finalize；
- 原文证据校验、账本和审计产物。
- `ai_notes` 手动共学包及 prepare/finalize 内部命令；
- 三个 v1 共学 Schema、四种运行状态和三十天运行产物保留；
- GitHub 仓库/Release/PR/Issue/tree 固定版本解析；
- 双侧证据、许可证风险、自有文件指纹和明确反馈校验；
- 人工 GitHub URL 提名对应的单项目 prepare/finalize 入口；
- 授权项目登记、Git HEAD/工作区快照绑定和越界读取阻断；
- 四类明确反馈、关联冷却事件和不把沉默推断为反馈的账本边界；
- 正反馈后的紧凑关联快照、明确关注 commit 游标和实验交接契约；
- YAML 策略、JSONL 运行账本、JSON 证据快照和三个版本化 Schema；
- GitHub 限额 `partial` 降级、确定性错误 `failed` 审计和安全重试；
