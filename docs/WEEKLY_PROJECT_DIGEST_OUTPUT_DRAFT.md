## 一、八个内容栏目

按用户确认，语言分类统一为“开源项目”，Skills、游戏及“博客、帖子与访谈”独立成栏；AI 应用、Agent 框架与编排、MCP 服务与连接器、模型与运行工具也直接作为一级栏目，不再保留“人工智能”上级分类或前缀。每个条目只选一个主栏目，不要求每期所有栏目都有内容；空栏目不显示。

| 栏目 | 内容范围 | 主要收什么 |
| --- | --- | --- |
| 开源项目 | 效率工具、知识管理、创作工具、开发工具、数据与服务管理 | 原来分散在 C / Go / Python 等语言栏目的通用应用和工具 |
| Skills | 按任务用途标注即可 | 给 Agent 使用的操作方法、技能包与可重复流程 |
| AI 应用 | 写作、搜索、图像、AI 编程、成品 Agent 等 | 可直接交代任务、以 AI 为主要能力的成品应用 |
| Agent 框架与编排 | Agent 开发框架、SDK、多 Agent 编排与运行组件 | 用来开发自己的 Agent、定义工具和执行流程的组件；包含重要更新 |
| MCP 服务与连接器 | MCP 服务、工具连接组件 | 主要用于连接 Agent 与外部系统的组件 |
| 模型与运行工具 | 模型、本地推理、部署工具 | 只选对实际使用有意义的变化 |
| 游戏 | 网页小游戏、独立游戏、开源游戏、游戏开发工具 | 可玩的作品、玩法启发、Game Jam 作品以及引擎 / 编辑工具 |
| 博客、帖子与访谈 | 作者博客、社区帖子、人物访谈、经验复盘 | 有实际启发的观点、开发方法、产品经验和案例；提供原文、作者及日期 |

“开源项目”是通用工具栏目，其他栏目也可以开源。按条目的主要交付物和用途归类：技能包归 Skills，可玩的作品或专门游戏开发工具归游戏，以观点、方法或人物经验为主要阅读价值的内容归博客、帖子与访谈；AI 成品应用（含 AI 编程工具和成品 Agent）归 AI 应用，开发 Agent 所用的框架、SDK 和编排组件归 Agent 框架与编排，以 MCP 服务或工具连接为主要交付物的归 MCP 服务与连接器，模型及其推理、部署工具归模型与运行工具；其余通用工具归开源项目。普通应用增加 AI / MCP 功能后不必搬栏，成品应用支持多 Agent 协作也不自动归为开发框架。仅介绍某个项目的博客或帖子通常作为该项目的来源；只有文章本身值得推荐阅读时才进入内容栏目，同一内容不重复收录。

“自托管”“MCP”“API”“CLI”“浏览器插件”“Windows / macOS / Linux / Android / iOS”作为标签；CLI 并不专属于 AI 工具。只写影响使用决定的标签，通常 2—4 个。编程语言默认省略，只有二次开发建议确实依赖它时才写。各栏目再标“新发现 / 重要更新 / 新闻事件”，首次发现早于本期时标“往期候选”及首次发现日期，不另建两套栏目。

栏目区分项目类型，“新发现 / 重要更新”区分报道性质。开源项目精选以介绍不同项目为主；Agent 框架与编排保留独立栏目，允许持续追踪固定框架的重要迭代，也可以介绍有实际差异的新框架。不要求每期出现新框架；已收录项目的更新只写变化和影响，不重复完整介绍，没有合格内容则省略该栏目。

来源清单见 [周报栏目与来源对照](WEEKLY_PROJECT_DIGEST_SOURCES.md)，聚合、精选和榜单单独列出，不作为新的内容栏目。

## 二、每期的阅读顺序

### 1. 标题、导语与目录

标题包含榜单类型及自然周期期号，标注统计日期、实际采集与定稿日期。用不超过三句话点出重点及理由，再列有内容的栏目目录；重点推荐从下方正文中选，不另凑条数、不重复完整介绍。周榜固定 3 个重点项目，非阅读项目少于 3 个时按实际数量；日榜与月榜根据阅读价值标记重点。标题根据真实内容概括，不以未经核实的效果或收入作标题。

### 2. 分栏目精选正文

按八个栏目分组，新发现项目、已有项目的重要更新、AI 新闻与博客、帖子、访谈共用名额；重点项目在所属栏目内标记，包含在总数中。日榜偏重有实际影响的 AI 动态与直接可用工具；周月偏重成熟实用项目、方法和重大变化。不设新闻比例或栏目的硬性配额，不以每天新项目数量凑数。

| 榜单 | 条数与阅读任务 | 不足时 |
| --- | --- | --- |
| 日榜 | 目标 5～8 条，简短写清用途、亮点和入口 | 交付实际结果并说明缺口 |
| 周榜 | 目标 20～25 条、3 个重点，展开场景和亮点 | 交付实际结果并说明缺口 |
| 月榜 | 至少 20 条，逐项说明保留价值与适用读者 | 保留草稿，按原月归属有界补采，满 20 条再定稿 |

跨级允许重复；周榜对日榜内容补充介绍，月榜重新评价，不能只是拼接已发短文。同级已交付内容只有尚未在该级报道的重要更新才可重推。

以适合手机阅读的短文为主，不强制放整期宽表格。每项采用“名称与一句话用途 → 介绍段落 → 官方入口与必要标签”的顺序；需要比较少量并列信息时才使用简表。

2026-10-05 用户提供 HelloGitHub 项目介绍截图并明确“重要的部分在于发现项目”。以下发现式介绍取代原先七项覆盖要求：

1. **名称与一句话用途**：让读者迅速理解它是什么、能做什么。
2. **两三个代表性亮点**：说明值得点开的功能、场景或有趣之处，按原文选择，不罗列全部功能。
3. **官方链接**：提供继续了解的入口；有帮助且取得可用资料时加一张配图或演示入口。

使用条件、限制、安装步骤、输入输出、操作链和下一步建议不再逐项必填，也不要求每项有独立的适用读者标签。少写这些信息本身不是描述缺失，不作为拒绝推荐的理由。后台仍保存事实卡、来源、核验及新旧状态；这些核对材料不必全部展示给读者。正文写出的主张要准确：不能把付费路径写成免费，把可选功能写成默认，或把片段、演示入口写成实测。可缩小介绍范围，无需补写一份使用说明。

日榜保持简短；周榜 3 个重点项目各约 250～400 字，展开场景、亮点和值得关注的理由，其余条目各约 100～150 字；月榜增加逐项保留理由。地址、标签和来源说明可独立一行；每项保留 1—2 个关键来源，更多核验记录收在文末。正文不用堆砌证据编号，star 数和语言占比默认不展示。

游戏卡突出核心玩法和试玩入口；闭源游戏可作为玩法观察，不能暗示可 Fork，未试玩不能宣称已验证好玩或留存。Skills 卡突出方法及适用 Agent，MCP 卡突出连接什么服务。设备、认证、费用和升级步骤按本次介绍需要选写，不做栏目必填清单。

博客、帖子与访谈使用内容卡：标题与原文链接、作者 / 受访者及日期、核心观点、值得读的理由、可以借鉴的做法。使用门槛改为阅读前提、语言或访问条件等必要信息，不要求源码和安装说明。以实际读到的正文、听看的内容或可核对文字稿为依据，区分作者观点、个人经历和独立证据；未取得内容不能只凭标题写总结。

重要更新卡使用“以前怎样 → 现在怎样 → 对使用有什么影响”，不列纯版本号堆砌。同级已推荐、没有新增实质变化的项目不重推，同一更新换措辞不能绕过历史去重。技术框架只有能说明对具体使用场景的直接影响时才入选。

新闻使用 `kind=news`，仍选八主题之一，不增第九栏。模型公告归模型与运行工具，产品变化归 AI 应用；行业动态按博客、帖子与访谈处理，但采用新闻卡而非访谈卡。写清具体变化、事件日期、影响人群、适用范围/行动、官方原文及未知项；不要求作者/受访者、源码、许可证或安装说明，不把宣传效果当作实际效果。总精选条数包含新闻，但新闻必须标注，不写成“全部是开源项目”。周月重用新闻要解释持续影响。

工具介绍补充使用依据与读者门槛：可查看演示、实际操作说明或独立使用案例分别标明，Star 仅作辅助；周月说成熟/稳定时要有依据。没有相应证据则观察，不能写成实测结论。纯编译测试/CI/代码内务工作流和实际树莓派硬件不推荐，CLI/MCP/Skills 按实际用途判断。

### 3. 开发机会观察

最多 2 条，独立于项目场景分类；没有充分证据就不展示这个栏目。

| 用户遇到的问题 | 谁有这个问题 | 现有方案与不足 | 原文证据及日期 | 可以验证的小切口 | 尚未确定的事 |
| --- | --- | --- | --- | --- | --- |
| 具体问题 | 具体人群 | 已核对的当前功能 | 用户反馈原文 | 访谈、手工服务或小原型 | 重复出现频率、付费意愿等 |

“我想做一个”不自动成为开发机会；应有可引用的用户问题，核对是否早已解决，并给可执行的验证。区分作者宣传、独立用户反馈和自己的推测。项目适合自用，不代表适合创业；机会也不等于现在就 Fork 开发。

### 4. 来源与未核实事项

简短列出本期实际初筛、深核与入选数量、实际读取的来源、失败渠道、缺少采集的日期及未验证的关键问题。这里是信息来源说明，不再按平台重发一遍项目列表。明确排除的热门项目仅在有解释价值时用一行说明，不另开长榜单。

正文及入选清单按 [运行流程](WEEKLY_PROJECT_DIGEST_WORKFLOW.md) 本地归档，由同一结构化清单生成正文，避免正文与索引错配。正式交付附已归档文件链接与对应日／周／月历史入口；月榜不足 20 条只说明草稿与缺口。不能只在聊天中发完便丢失历史索引，也不能将本地归档写成已发布公众号。

可在末尾留一句反馈入口：“想试 / 收藏 / 想看哪个方向”，用于后续选择；不强迫每期反馈，也不把单个读者已有类似工具当成面向所有读者的排除理由。
