## 一、五个内容栏目

按本轮用户修订，语言分类统一为“开源项目”，保留 Skills、人工智能、书籍与教程，并新增独立游戏栏目。每个条目只选一个主栏目，不要求每周所有栏目都有内容；空栏目不显示。

| 一级栏目 | 二级分类 | 主要收什么 |
| --- | --- | --- |
| 开源项目 | 效率工具、知识管理、创作工具、开发工具、数据与服务管理 | 原来分散在 C / Go / Python 等语言栏目的通用应用和工具 |
| Skills | 按任务用途标注即可 | 给 Agent 使用的操作方法、技能包与可重复流程 |
| 人工智能 | AI 应用 | 写作、搜索、图像等以 AI 为主要能力的成品应用 |
| 人工智能 | Agent 与自动化 | AI 编程工具、智能体、开发框架、多 Agent 编排；包含重要更新 |
| 人工智能 | MCP 与工具连接 | MCP 服务和主要用于连接 Agent 与外部系统的组件 |
| 人工智能 | 模型与运行工具 | 模型、本地推理、部署工具；只选对实际使用有意义的变化 |
| 游戏 | 网页小游戏、独立游戏、开源游戏、游戏开发工具 | 可玩的作品、玩法启发、Game Jam 作品以及引擎 / 编辑工具 |
| 开源书籍与教程 | 书籍、教程、实战案例 | 有实际学习价值的材料；区分有开放许可证与仅免费阅读 |

“开源项目”是通用工具栏目，其他栏目也可以开源。归类顺序按条目的主要交付物和用途：技能包归 Skills，可玩的作品或专门游戏开发工具归游戏，教学材料归书籍与教程，AI 为核心或 MCP 为主要接口产品的归人工智能，其余通用工具归开源项目。普通应用增加 AI / MCP 功能后不必搬栏。

“自托管”“MCP”“API”“CLI”“浏览器插件”“Windows / macOS / Linux / Android / iOS”作为标签；CLI 不仅限于人工智能。只写影响使用决定的标签，通常 2—4 个。编程语言默认省略，只有二次开发建议确实依赖它时才写。各栏目再标“新发现 / 重要更新”，不是另建两套栏目。

来源清单见 [周报栏目与来源对照](WEEKLY_PROJECT_DIGEST_SOURCES.md)，聚合、精选和榜单单独列出，不作为新的内容栏目。

## 二、每期的阅读顺序

### 1. 本周先看

用不超过三句话点出最值得试的 1—2 项及理由；从下面项目中选，不另凑条数。标注统计日期、实际收集日期。

### 2. 实用项目精选

最多 5 个，按上述五个内容栏目分组；只有 2 个合格就只发 2 个。新发现项目与已有项目的重要更新共用这 5 个名额，不为新增栏目增加凑数要求。

先给一张速览表：

| 分类 | 项目 | 能帮你做什么 | 值得看的理由 | 使用门槛 | 建议 |
| --- | --- | --- | --- | --- | --- |
| 开源项目 / 知识管理 | 项目名与官方链接 | 具体任务 | 与已有工具的差异 | 系统、安装、模型费用等必要信息 | 试用 / 收藏 / 关注 |

之后每个项目给一张短介绍卡，包含以下字段：

1. **名称、官方地址与标签**：提供可以继续查看的入口。
2. **一句话用途**：用用户能理解的操作描述，不复述技术口号。
3. **适用场景**：谁在什么情况下需要它，给一个具体例子。
4. **值得看的理由**：相对现有方案有什么不同；没有比较证据就说未完成比较，不凭空写“更好”。
5. **使用条件与主要限制**：系统、部署方式、硬件、是否另需付费服务，以及影响使用的限制。
6. **核验与时效**：只读了文档 / 已查看演示 / 已本机测试；本周新发布 / 本周新发现的旧项目 / 重要更新 / 历史精选。新发现不能写成新发布。
7. **建议与下一步**：为什么建议试用、收藏或继续关注；给出试玩、文档或安装说明链接。没有跑过就不能称“好用”“稳定”。

这些是必须覆盖的信息，不要求机械列七个小标题；一张卡通常 150—250 字。每项保留 1—2 个关键来源，更多核验信息收在页尾，避免每格塞满证据编号。star 数和语言占比默认不展示。

游戏卡补充“核心玩法、试玩入口、支持设备、是否开源、可借鉴的设计”；闭源游戏可作为玩法观察，明确标记，不能暗示可以 Fork。未试玩不能宣称好玩或有留存。Skills 卡补充“适用 Agent / 依赖工具”，MCP 卡补充“连接什么服务 / 认证和费用要求”，更新卡补充“是否需要采取升级行动”。

重要更新卡使用“以前怎样 → 现在怎样 → 对使用有什么影响”，不列纯版本号堆砌。已经推荐、没有实质变化的项目不重推。技术框架通常不进入主刊，除非能说明对具体使用场景的直接影响。

### 3. 开发机会观察

最多 2 条，独立于项目场景分类；没有充分证据就不展示这个栏目。

| 用户遇到的问题 | 谁有这个问题 | 现有方案与不足 | 原文证据及日期 | 可以验证的小切口 | 尚未确定的事 |
| --- | --- | --- | --- | --- | --- |
| 具体问题 | 具体人群 | 已核对的当前功能 | 用户反馈原文 | 访谈、手工服务或小原型 | 重复出现频率、付费意愿等 |

“我想做一个”不自动成为开发机会；应有可引用的用户问题，核对是否早已解决，并给可执行的验证。区分作者宣传、独立用户反馈和自己的推测。项目适合自用，不代表适合创业；机会也不等于现在就 Fork 开发。

### 4. 来源与未核实事项

简短列出本期实际读取的来源、失败渠道、未验证的关键问题。这里是信息来源说明，不再按平台重发一遍项目列表。明确排除的热门项目仅在有解释价值时用一行说明，不另开长榜单。

可在末尾留一句反馈入口：“想试 / 收藏 / 已有替代 / 不感兴趣”，用于后续选择；不强迫每期反馈。
